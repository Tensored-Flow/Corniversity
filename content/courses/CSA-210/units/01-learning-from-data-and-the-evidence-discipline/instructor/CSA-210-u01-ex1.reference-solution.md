## Reference reasoning (instructor only)

The scenario is synthetic; the problems are deliberately layered so that a learner who finds one leak and stops has not finished.

**(a) Inventory of problems.**

1. *Step 2, target leakage.* `ticket_opened_this_week` is produced by the fault-detection process the label describes: tickets are opened after a fault is detected, in the failure week or the week before. The feature is therefore a near-copy of the label (or of the label shifted by one week) and is not available at the start of the week when a prediction would be used. The rule "predict failure iff a ticket was opened" would by itself score close to the reported figure.
2. *Step 3, temporal leakage.* The label of machine $m$ in week $t$ is "fails in week $t+1$". The record of machine $m$ for week $t+1$ carries exactly that information (its sensors during a failure week, its own ticket flag). With a uniform shuffle, roughly 80% of test records have their machine's following week in the training set, so the model can learn the test labels through the neighbouring record. Consecutive weeks are also strongly autocorrelated, which inflates performance even without the direct label route.
3. *Step 3, group leakage.* Each machine contributes 20 records; on average 16 land in training. The model can learn machine identity (sensor baselines are machine-specific) and each machine's typical failure pattern rather than a transferable mapping from sensors to failures. A new machine would not enjoy this.
4. *Step 5, selection leakage.* The reported test accuracy is the maximum of 30 noisy estimates. Even if every configuration had the same true accuracy, the maximum of 30 roughly normal estimates exceeds the mean by about two standard errors; with 1,000 test records and accuracy near 0.95 the standard error is $\sqrt{0.95\cdot0.05/1000}\approx0.007$, so the selection alone can add about one to one and a half points. The test set has been used as a validation set and no unbiased estimate remains.
5. *Step 1, preprocessing leakage.* Imputation and standardisation statistics include test rows. This is a real leak but usually a mild one (the mean and variance of 5,000 rows barely change when 1,000 are removed); it is nonetheless a protocol error because the fitted statistics must be computed on training data only.

**(b) Why 97.4% is not evidence.** The base rate is 6%, so a model that never predicts a failure has accuracy $0.94$. The reported 97.4% is 3.4 points above that trivial baseline, and the inventory above offers several routes that could supply more than 3.4 points on their own: the ticket feature alone (a label proxy), the next-week record of the same machine (the label itself), and the selection among 30 configurations (one to two points of optimism). Even the arithmetic of accuracy hides what matters on a 6% base rate: 97.4% is compatible with recall on failures anywhere from very high to mediocre. Without the base rate, per-class figures and a leak-free protocol the number is not evidence of predictive skill.

**(c) A defensible ranking** (largest inflation first): target leak via the ticket (near-copy of the label) ≥ temporal leak via the same machine's next-week record (also the label, slightly less directly) > group leak (identity shortcuts) > selection on the test set (one to two points) > full-data standardisation (fractions of a point). Accept other orderings with a coherent argument, in particular swapping the first two; the key judgement is that the first two can account for essentially all of the surplus over baseline while the last is minor.

**(d) Corrected protocol** (one acceptable version).

- Split by machine and by time: hold out 50 machines entirely as the test group; within the remaining 200, use weeks 1–14 for training and 15–17 for validation; evaluate on the test machines' weeks 18–20 (or all their weeks, for a pure new-machine test). State which.
- Admissible features: only values known at the start of the prediction week; remove `ticket_opened_this_week` and any field written after fault detection.
- Fit imputation and standardisation on the training portion only and apply the fitted transform to validation and test.
- Choose hyperparameters on the validation split (grouped by machine); never on the test set.
- Evaluate on the test set exactly once with the chosen configuration.
- Report: base rate (6%), majority baseline (94%), a simple baseline (logistic regression on the admissible features), the confusion matrix and precision/recall at the operating threshold, the number of seeds with mean and spread, the test-set standard error, and the exact split definition.

**Alternative valid approaches.** A time-only split (train weeks 1–14, test 18–20 on all machines) addresses the temporal leak but not new-machine generalisation; mark it as partially met on the protocol unless the learner states that limitation. Grouped cross-validation with the test machines held out throughout is a fully acceptable alternative.

**Common gaps.** Finding the ticket leak and stopping; calling the shuffle "fine because it is random"; computing the baseline as 6% instead of 94%; proposing a validation set but still reporting the best of several test runs; omitting the admissibility rule for features.
